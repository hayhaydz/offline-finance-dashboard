## 4. BLOCKER — dev DB migration journal (fix before cut)

`tests/integration/migration-journal-sync.test.ts` fails: `storage/dev-plain.db`'s `__drizzle_migrations` table is missing the sha256 hashes of `0010_great_major_mapleleaf.sql` and `0011_third_obadiah_stane.sql`.

- **Root cause** (per the test's own header): the Active-Dev direct-SQL path applied the schema without writing the migrator's journal.
- **Hazard:** the next fresh dev boot (vite preview / adapter-node) replays those migrations and dies on "duplicate column" — the exact class of the 2026-10-29 production boot crash.
- **Production is NOT affected:** `prod.db` is journaled only through 0007 and will legitimately apply 0008–0011 through the migrator on first v3 boot.
- **Fix (documented remedy, needs explicit approval per the DB lock):** insert each file's sha256 into the dev DB's journal:

```bash
npx tsx -e '
import fs from "node:fs"; import crypto from "node:crypto";
import Database from "better-sqlite3";
const db = new Database("storage/dev-plain.db");
for (const f of ["0010_great_major_mapleleaf.sql", "0011_third_obadiah_stane.sql"]) {
  const hash = crypto.createHash("sha256")
    .update(fs.readFileSync(`src/lib/db/migrations/${f}`, "utf8")).digest("hex");
  db.prepare("INSERT INTO __drizzle_migrations (hash, created_at) VALUES (?, ?)")
    .run(hash, Date.now());
  console.log("journaled", f, hash.slice(0, 12));
}
db.close();'
```

Then re-run `npm test` — must be 1178/1178 before cutting.

## 8. Migration challenges & behavioural changes (ranked)

1. **TOTP + backup codes are gone.** Login becomes password-only until a WebAuthn PRF device slot (L2, 2-of-2) is enrolled on `/settings/security`. Any printed v1.x backup codes become invalid. If you currently log in with a TOTP app, expect that prompt to disappear — this is the release working as designed.
2. **Rollback is coupled:** v1.1.0 code selects the dropped TOTP columns, so a code-only rollback against the migrated DB breaks. Rollback = **restore `prod.db.pre-update-3.0.0` AND `git checkout release/v1.1.0` together**, then rebuild + restart.
3. **First boot runs 4 migrations + keyring boots sealed** — brief window where the app redirects to `/unlock` after login. Do the restart at a quiet moment; verify before relying on it.
4. **UI paradigm shift:** full-viewport desktop shell, `viewport width=1280` — phones now render a zoomed-out desktop (deliberate v3 decision, no mobile design). If you use the app on mobile, this is the most visible change.
5. **Large imports now queue** (sealed background `import_jobs` queue) instead of running inline — large bank-statement CSVs will show job progress on `/settings/data`.
6. Dev-only: `storage/dev-plain.db` needs the §4 journal fix; `storage/dev.db` / `dev-encrypted.db` are stale older-era DBs (not gated by tests).

## 10. Versioning model from v3.0.0 onward

- **`main` = trunk** (now identical to shipped v3). `release/vX.Y.Z` branches = immutable snapshots cut from main at deploy time. No tags. The production clone tracks one release branch at a time.
- **Semver for this repo:**
  - `PATCH` (3.0.Z) — bug fixes only, zero schema changes.
  - `MINOR` (3.Y.0) — additive features; nullable columns and new tables are OK.
  - `MAJOR` (X.0.0) — destructive migrations, auth/security-model changes, UX paradigm shifts.
- **Iterating on v3:** work lands on main (or short-lived branches merged to main); cut `release/v3.Y.Z` when ready to deploy. **Hotfix rule (the v1.1.0 lesson):** fix on main first, cherry-pick to the live release branch immediately, deploy the release branch — never let the release branch and main drift.
- **v4:** run the next loop as a long-lived branch off main (like ultimate-3.0 did), merge/fast-forward main at loop close, then cut `release/v4.0.0`. Loop names (`ultimate-N`) stay internal; shipped versions are semver. Because main now equals shipped v3, the next loop starts from production reality — no repeat of the v1.1.0-era drift where hotfixes lived only on the release branch.
